Code-Vault review

jimjamscott22/Code-Vault · reviewed read-only on Oct 22, 2026, at the latest commit on the default branch (Oct 20)

TL;DR: This is a well-built local-first snippet manager. The layering is clean, the shared Rust core has real unit tests, and CLAUDE.md is excellent onboarding. The main risks are data integrity: imports and migrations don't use transactions, and the backup copies a WAL database file directly. There's also a wide-open webview: CSP is off, and the IPC commands accept any file path.

What it is

CodeVault is a desktop snippet manager. It stores code, shell one-liners and configs with tags, folders, tag categories, markdown notes and {{placeholder}} templates, all in a local SQLite file with no accounts and no cloud.

FrontendReact 19, TypeScript 5.8, Vite 7, Tailwind 3, CodeMirror 6 (@uiw/react-codemirror), Zustand 5, cmdk (package.json)
BackendTauri 2 and Rust with rusqlite. The logic lives in a shared crate, crates/codevault-core. There's also a standalone CLI, crates/codevault-cli.
DataSQLite in WAL mode with foreign keys on (codevault-core/src/lib.rs:146), versioned migrations (:157-228) and daily rotating backups (:239-264)

Structure: what's good

  • The layering is clean: core crate → thin #[tauri::command] wrappers (src-tauri/src/commands.rs) → one typed IPC layer (src/lib/api.ts) → Zustand store. Because the CLI and GUI share one data layer, they can't drift.
  • Every query is parameterized. I found no SQL built with string formatting from user input. SNIPPET_SELECT is just a constant spliced in.
  • The Rust unit tests cover import strategies, markdown splitting, the export round-trip, folders and date math (lib.rs:910+). template.rs also has its own tests, per CLAUDE.md.
  • Editor saves are debounced, with a Ctrl+S flush (src/components/SnippetDetail.tsx:93-137).
  • CLAUDE.md is one of the best repo guides I've seen. It documents the four edits needed per command, the IPC casing rules and the dual-filter gotcha.

Security

HighCSP is disabled. src-tauri/tauri.conf.json has "security": {"csp": null}. In Tauri, any script injection in the webview can call every registered command. That matters because of the next item.
HighIPC commands take arbitrary filesystem paths. export_vault runs std::fs::write(&path, json) on any path the frontend passes (commands.rs, export_vault). import_vault and import_markdown read any path, and import_markdown_dir lists any directory. The dialog plugin chooses those paths today, but the Rust side never checks them. If you pair this with a missing CSP, an XSS bug (say, in future markdown-notes rendering) turns into "overwrite any file the user can write". The fix is either to do the dialog in Rust and never accept a raw path, or to at least enforce an extension and reject paths outside a user-picked scope.
Medopener:allow-open-path is granted in src-tauri/capabilities/default.json with no path scope. I couldn't tell if that's needed. If it's only used for "open data folder", scope it to $APPDATA.

Data integrity and performance

HighMigrations aren't atomic. migrate() runs each migration with execute_batch and then writes the version as a separate statement (lib.rs:216-224), with no transaction around them. Migration v2 is a CREATE TABLE plus an ALTER TABLE ADD COLUMN (:196-202). If it dies halfway, the next launch retries it and fails on "duplicate column". The vault is then stuck until someone fixes it by hand. Also, .unwrap_or(0) on the version read (:168) quietly treats any read error as "fresh DB".
HighThe backup copies a live WAL database with fs::copy (lib.rs:248). With journal_mode=WAL, recent commits can still be sitting in vault.db-wal, so the backup can be stale or inconsistent. Use VACUUM INTO or rusqlite's backup API instead.
MedImports aren't wrapped in a transaction. import_vault_json loops over snippets and stops at the first error with ? (lib.rs:634-636). You end up with half an import and no report of what landed. import_markdown_dir does the same thing per file (commands.rs). create_snippet and insert_full also do the insert and the tag writes as separate statements (:300-319, :677-696). One transaction per import would fix correctness, and with SQLite it's also a big speedup on large imports.
MedUnknown import strategies quietly mean "rename". strategy: &str matches "skip" and "overwrite", and anything else falls through to rename (lib.rs:658-672). A serde enum would turn typos into errors.
LowLookups that will get slow: import conflict checks and unique_title query snippets.title, which has no index (the only index is idx_snippets_folder_id). set_snippet_tags runs 3 statements per tag. Search uses LIKE '%q%' on the code and notes columns, which is fine for hundreds of snippets. Once you reach thousands, look at SQLite FTS5.

Code smells and bugs

  • The two search paths disagree, which CLAUDE.md says they shouldn't. The client-side filteredSnippets checks title, code and tags (src/lib/store.ts:352-354). SQL search_snippets also checks notes (lib.rs:540). The client side also runs t.includes(q) on tags without lowercasing them, so if a tag has a capital letter, a search on the lowercased query won't match it.
  • Each of the 25 commands repeats state.0.lock().map_err(|_| "db lock poisoned")? (commands.rs). A small with_conn(|c| ...) helper would remove about 50 lines and give you one place to add logging.
  • Errors cross IPC as plain Strings (type CmdResult<T> = Result<T, String>), so the UI can't tell "not found" from "disk full".
  • Commands are sync and hold the global Mutex across file I/O. For example, import_markdown_dir reads every file while holding the lock. Big imports will freeze every other UI call.
  • Leftover scaffolding: src/assets/react.svg, public/vite.svg, public/tauri.svg and a 7.8 KB src/lib/mockData.ts. Check whether any of these are still imported before you delete them.
  • There are two Cargo.lock files: a root Cargo.lock and src-tauri/Cargo.lock. With a root workspace, the inner one is probably stale.

Tests, CI and docs

  • No CI. The tree has no .github/ directory, so nothing runs cargo test, clippy or tsc on a PR, and the good Rust tests only help if you remember to run them.
  • No frontend tests or linter. CLAUDE.md says so outright. The best candidates for first tests are filteredSnippets/groupedSnippets in store.ts and src/lib/template.ts. The TS template parser has to stay in sync with template.rs, so share test vectors between the two (for example a JSON fixture both suites read).
  • The docs are strong: README (12 KB), SPEC, IMPLEMENTATION_PLAN, PERFORMANCE_NOTES and the plans under docs/superpowers/. They don't have a short security or threat-model note.

Improvements worth doing

Reliability

1. Transactional migrations, imports and backups. Wrap each migration and its version write in a single conn.transaction(). Do the same for each import call. Switch the backup to VACUUM INTO. This is a small diff, and it protects the one thing users can't get back: their snippets.

Security

2. Turn on a CSP and stop trusting raw paths. Set a strict CSP (default-src 'self'; style-src 'self' 'unsafe-inline'; CodeMirror needs inline styles). Move the save and open dialogs into Rust so export_vault and import_* never accept a path from JS. Scope opener:allow-open-path.

DevEx

3. Add a GitHub Actions workflow. Run cargo test -p codevault-core + cargo clippy -- -D warnings + pnpm build on every PR. Add Vitest for store.ts filtering and template.ts, with shared template fixtures.

Performance and UX

4. FTS5 search with one search path. Add an FTS5 virtual table over title, description, code, notes and tags, and route the search box through it. That fixes the client/SQL mismatch, adds ranking and highlighting, and scales well past what in-memory filtering can handle.
5. Make import results visible and undoable. Return per-item results, including which files failed and why, and show them in a toast or modal. Take an automatic backup right before every import so "undo" is just a restore.

Start here

  1. Wrap migrate() steps and their version insert in a transaction, and stop swallowing the version-read error (lib.rs:157-228).
  2. Replace the fs::copy backup with VACUUM INTO (lib.rs:248).
  3. Set a real CSP in tauri.conf.json and validate or own file paths in export_vault/import_*.
  4. Wrap each import in one transaction and turn strategy into an enum.
  5. Add CI (cargo test + clippy + pnpm build).
  6. Line up client and SQL search: add notes, lowercase tags, and later move to FTS5.
  7. Clean up the leftover assets and the duplicate Cargo.lock, and add a with_conn helper.

Everything above was verified by reading files through the GitHub API. I didn't build or run the app, and line numbers refer to the default branch on Oct 22, 2026.
